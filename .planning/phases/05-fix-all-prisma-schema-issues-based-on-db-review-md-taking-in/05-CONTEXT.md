## Implementation Decisions

### User/Post orphan tables
- **D-01:** No schema change needed — User/Post models already removed from `schema.prisma`. DB tables from old init migration are cosmetic only.

### professions_id naming
- **D-02:** Rename `professions_id` → `profession_id` in model `professions_resources_amounts` (field, relation fields reference, composite @@id).
- **D-03:** Update all TypeScript code references: `src/modules/professions/professions.service.ts` (lines 88, 105) and `src/jobs/daily-production.job.ts` (lines 42, 78). No E2E test changes needed (tests only reference `people.profession_id`, not this table's FK).
- **D-04:** Generate a Prisma migration for the rename: `npx prisma migrate dev --name rename_professions_id_to_profession_id`.

### Index naming and new indexes
- **D-05:** Add explicit `map:` names to every `@@index` directive. Use descriptive names: `{table}_{column}_idx` (e.g., `admissions_camp_id_idx` instead of generic `fk_camp_id_idx`). This makes EXPLAIN output unambiguous even when indexes have the same column names across tables.
- **D-06:** Add new indexes on frequently-queried date columns per db-review §9.4:
  - `admission_requests.created_at` — for filtering admissions by date
  - `expeditions.departure_date` — for departure date queries
  - `expeditions.expected_return_date` — for return date range queries
  - `inventory_log.logged_at` — for audit log date filtering
- **D-07:** Generate a Prisma migration for index changes: `npx prisma migrate dev --name add_index_names_and_date_indexes`.

- Whether to combine the profession_id rename and index changes into one migration or two

### Established Patterns
- FK naming: `[singular_model]_id` (e.g., `camp_id`, `person_id`, `resource_type_id`)
- Model naming: PascalCase in Prisma, snake_case in DB via `@@map()`
- Index naming: currently auto-generated by Prisma; moving to explicit `map:` names
- Migration naming: descriptive, kebab-case timestamps (e.g., `20260320123000_add_camp_ai_context_prompt`)
