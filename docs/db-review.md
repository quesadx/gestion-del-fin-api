### 3.6 Uso de palabras reservadas del motor como nombres de objetos

⬛ **Candidatos a revisar en MySQL**:

- `status` (campo en `camp_transfers`, `camps`, `expeditions`, `persons`): en MySQL 8.x, `STATUS` es una palabra reservada. En el schema de Prisma no requiere escape porque Prisma usa backticks automáticamente en MySQL, pero en SQL manual podría causar problemas.
- `name` (en `achievements`, `camps`, `professions`, `resource_type`, `roles`): `NAME` es una palabra reservada en algunas versiones de MySQL. Nuevamente, Prisma lo maneja con backticks automáticamente.
- `type` (en `camp_transfer_item`): `TYPE` es palabra reservada en MySQL.

En la práctica no causa errores porque Prisma escapa todos los identificadores con backticks en las queries generadas. Sin embargo, podría ser problemático en queries SQL manuales sin escape.

⬛ **Casos detectados**:

1. Migración `"20260510030706_add"` — nombre extremadamente genérico para una migración. No indica qué se está agregando (agrega `session_version` a `users`).
2. `delta` en `inventory_log` — aunque es un término técnico válido para "cambio en cantidad", podría resultar ambiguo para desarrolladores sin contexto. Alternativa: `quantity_change`.
3. `ai_decision` vs `final_decision` en `admission_requests` — razonable dado el contexto de IA, pero podría confundir si no se tiene el dominio claro.

## Sección 6 — Normalización

### 6.1 Primera Forma Normal (1FN)

#### 6.1.1 Valores atómicos
■ **No se detectan columnas con valores potencialmente no atómicos.**

Las columnas `TEXT` (`applicant_skills`, `health_notes`, `background_notes`, `notes`, `skills_summary`, `description`, `reason`, `ai_reasoning`) almacenan texto libre descriptivo, lo cual es atómico aunque largo. No son listas ni valores múltiples estructurados.

#### 6.1.2 Columnas repetidas del mismo concepto
■ **No se detectan grupos de columnas repetidas** (ej. `telefono1`, `telefono2`...).

La tabla `camp_transfers` tiene múltiples campos de aprobación (`approved_by_source`, `approved_by_target`, `approved_source_at`, `approved_target_at`) que representan dos etapas distintas del flujo de aprobación — no son repeticiones del mismo campo sino fases diferenciadas del proceso de negocio.

### 6.2 Segunda Forma Normal (2FN)

Aplica a 4 tablas con PK compuesta:

1. `expedition_allocated_resources` `@@id([expedition_id, resource_type_id])`: Solo tiene el campo `amount` adicional. El `amount` depende de ambas columnas PK. ■
2. `expedition_found_resources` `@@id([expedition_id, resource_type_id])`: Solo tiene `amount`. Mismo análisis. ■
3. `expedition_members` `@@id([person_id, expedition_id])`: No tiene atributos adicionales. ■
4. `professions_resources_amounts` `@@id([professions_id, resource_type_id])`: Solo tiene `amount`. Depende de ambas columnas PK. ■

■ **No se detectan dependencias parciales en tablas con PK compuesta.**

### 6.3 Tercera Forma Normal (3FN)

#### 6.3.1 Dependencias transitivas potenciales

⬛ **Candidato a revisar en `person_status_log`**:
```prisma
old_status String @db.VarChar(20)
new_status String @db.VarChar(45)
```

Ambas columnas almacenan el estado como texto libre (no como FK a tabla de catálogo). Los estados de personas están definidos como `enum(persons_status)` en el schema de Prisma, pero el log los almacena como `VARCHAR`, lo que rompe la dependencia con el catálogo de estados.

Adicionalmente, los tamaños son inconsistentes: `VarChar(20)` vs `VarChar(45)` para el mismo tipo de dato (ambos deberían ser iguales ya que representan el mismo dominio de valores).

■ No se detectan otras dependencias transitivas evidentes.

#### 6.3.2 Atributos calculables o derivados almacenados

⬛ **Candidato a revisar**:
```prisma
inventory.quantity Decimal @default(0.00) @db.Decimal(12, 2)
```

Este campo parece ser el saldo actual del inventario, que podría calcularse sumando todos los registros de `inventory_log`. Sin embargo, mantenerlo como snapshot (valor actual desnormalizado) es una práctica válida de optimización de rendimiento, común en sistemas de inventario. Si es un valor calculado y mantenido manualmente, existe riesgo de inconsistencia con `inventory_log`.

■ No se detectan otros atributos obviamente calculables.

### 6.4 Tablas de catálogo/dominio

#### 6.4.1 Tablas de catálogo separadas
■ **Se detectan 4 tablas de catálogo bien definidas**:

1. `roles` — catálogo de roles de usuario (admin, operador, etc.)
2. `professions` — catálogo de profesiones/oficios de supervivientes
3. `resource_type` — catálogo de tipos de recursos (comida, agua, medicinas, etc.)
4. `achievements` — catálogo de logros desbloqueables

Adicionalmente, `camps` actúa como entidad maestra que otras tablas referencian.

#### 6.4.2 Campos de estado almacenados como strings libres
⬛ **Detectado en `person_status_log`**:
```prisma
old_status String @db.VarChar(20) ← VARCHAR libre, no FK ni enum
new_status String @db.VarChar(45) ← VARCHAR libre, no FK ni enum
```

Estos campos deberían usar el mismo `enum persons_status` o al menos tener el mismo tamaño.

■ El resto de los campos de estado/tipo usan enums de Prisma correctamente:
- `camp_transfers_status`, `camp_transfers_type`, `camps_status`, `expeditions_status`, `inventory_log_log_type`, `persons_status`, `admission_requests_ai_decision`, `admission_requests_final_decision`

### 6.5 Nivel de normalización estimado

La BD se encuentra principalmente en **3FN**, con las siguientes excepciones menores:

- `person_status_log` almacena estados como `VARCHAR` en lugar de referenciar el enum/catálogo (violación menor de 3FN por dependencia no formalizada)
- `inventory.quantity` podría considerarse un dato derivado de `inventory_log` (desnormalización intencional y justificada para rendimiento)

El diseño general es sólido y está correctamente estructurado para un sistema de gestión de campamentos con múltiples entidades interrelacionadas.
